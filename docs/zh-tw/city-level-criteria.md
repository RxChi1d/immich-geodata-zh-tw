# City 層級的選擇條件

> 本文件定義 `cities500.txt` 的 `name` 欄（Immich 顯示的「城市」）應該放哪一個
> 行政層級，以及新增國家時如何驗證這個選擇。適用於官方圖資 handler 與
> LocationIQ 路線兩者。

## 1. 為什麼需要一條明確的條件

Immich 的反向地理查詢只回傳三格：

```sql
SELECT * FROM geodata_places
WHERE earth_box(ll_to_earth_public($1, $2), 25000) @> ll_to_earth_public(latitude, longitude)
ORDER BY earth_distance(...) LIMIT 1
```

回傳 `{country, state: admin1Name, city: name}`（`server/src/repositories/map.repository.ts`）。
`admin2_code` 以下的欄位 Immich 完全不讀，所以**行政層級的選擇就是在選 `name`
裡放什麼**，沒有第二個地方可以補救。

選得太粗，三格無法定位座標——印尼的 kabupaten 平均 3,705 km²，一張烏布拍的
相片顯示「巴釐省・吉亞尼亞爾縣」，範圍比雲林縣還大，而且那不是任何人用來指稱
烏布的名字。

選得太細，每個單位分不到足夠的點，標籤邊界會失準（見條件 2）。

## 2. 四個條件

條件 1 到 3 是硬條件，任一項不成立就往上一層。條件 4 是要量的取捨項，不是
閘門——低中文覆蓋率的結果是多數地名顯示原文，而那是回退鏈的正常行為。

### 條件 1：辨識性

**該層級的名稱是當地人與訪客用來指稱地點的名字。**

檢驗方式：把該層級的名字填進「國 + 一級行政區 + city」三格，問「這三格能不能
讓人認出座標在哪裡」。

- 通過：臺灣「臺灣・宜蘭縣・礁溪鄉」、日本「日本・神奈川県・箱根町」
- 不通過：印尼「印尼・巴釐省・吉亞尼亞爾縣」——該地叫烏布（Ubud），
  kabupaten 名不是使用者會說的那一個

注意這一項與中文無關。`Ubud` 即使是印尼文，辨識性也高於「吉亞尼亞爾縣」。
中文是條件 4 的事。

### 條件 2：密度

**該層級的每個單位要有足夠的代表點撐住邊界。**

| 指標 | 門檻 |
| :--- | :--- |
| 每單位點數中位數 | ≥ 5 |
| 只有 1 個點的單位比例 | < 10% |

Reason: Immich 取 25 km 內的最近鄰，所以標籤的實際邊界是這些點的 Voronoi
邊界。單位只有一個點時，它與鄰接單位的分界完全由兩點的垂直平分線決定，
跟真實行政區界無關——邊界附近的座標會被判給隔壁的行政區。點越密（尤其沿著
邊界），Voronoi 邊界越逼近真實邊界，誤判機率越低。

門檻取自實測：目前出貨的最稀疏層級是泰國的 อำเภอ（中位數 7、單點 1%），
品質可接受；而臺灣、南韓、泰國再往下一層的中位數全部掉到 1，即「每個單位
一個點」，那是門檻之下。

**剪枝不影響這一項的判斷。** prune 階段只刪除「刪了也不改變任何座標查詢結果」
的點——也就是被同標籤鄰點完全包住的內部點；邊界附近的點依定義不可刪。所以
密度要在剪枝**之前**衡量。

### 條件 3：層級一致

**同一個國家只能用一個行政層級。**

同一個行政單位內出現多種層級的名字，比整體粗一級更糟：使用者無法預期看到的
是什麼，而且點與點之間的標籤不一致會讓剪枝失效。

反例是 LocationIQ 路線修正前的馬來西亞：`normalizecity=1` 把九個層級的欄位
依序提升成 `city`，同一個 daerah 內最多出現 9 種不同名字。詳見
`data/locationiq/README.md`。

**這一項只管行政層級，不管語言。** 名稱的語言是逐名回退的——繁體中文 → 中文
（OpenCC 轉繁）→ 英文 → 來源原文，見
[全球翻譯處理](global-translation-processing.md#翻譯優先序)。所以同一個國家
裡一部分地名是中文、一部分是原文，是這條管線的正常結果，不是缺陷；每個
非 handler 國家都是這樣。

### 條件 4：中文覆蓋率（要量，但不是門檻）

**量該層級有多少比例的單位拿得到權威中文名，並接受它會隨層級變細而下降。**

這一項**不是通過／不通過的閘門**。名稱語言逐名回退（條件 3），所以低覆蓋率
的結果是「多數地名顯示原文」，不是壞掉。要量它，是因為換層級時中文覆蓋率
通常會一起變動，那是取捨的一邊：

| 國 | 層級 | 中文單位覆蓋 |
| :--- | :--- | ---: |
| 印尼 | kabupaten | 90% |
| 印尼 | kecamatan | 6.4% |

可接受的來源：該國官方圖資既有的中文欄位、Wikidata（須經 P131 parent 驗證，
見 [Wikidata 譯名的已知失效形態](wikidata-translation.md)）、國教院譯名表
（NAER，**僅適用於非 handler 國家**——handler 國家的名稱來自官方圖資屬權威值，
`naer_lookup.rs:240` 一律跳過，避免按名稱比對的誤配覆蓋掉正確名稱）。

**不接受機器音譯。** 沒有權威來源時留原文，不自行造譯名——錯誤的譯名比原文
更難辨識，而且會污染後續所有比對。

**覆蓋率低不是不接譯名的理由。** 6% 也要接：那 6% 正好是最知名的地點
（烏布、水明漾、庫塔），使用者最可能拍照的地方。

## 3. 各國實測

密度與中文覆蓋在**剪枝前**衡量（`data/handler/*_geodata.csv`、
`data/locationiq/MY.csv`）。馬來西亞一列取自 `feat/locationiq-address-level`
重查後的 19,903 點資料；該分支合併前，`data/locationiq/MY.csv` 仍是舊欄位的
791 點版本，數字不同。

| 國 | 選定層級 | 單位數 | 點/單位中位數 | 單點單位 | 中文單位 |
| :--- | :--- | ---: | ---: | ---: | ---: |
| 臺灣 | 鄉鎮市區 | 368 | 17 | 0% | 100% |
| 日本 | 市区町村 | 1,754 | 1 | 62% | 100% |
| 南韓 | 시군구 | 253 | 13 | 9% | 100% |
| 泰國 | อำเภอ | 927 | 7 | 1% | 94% |
| 印尼 | kecamatan | 7,377 | 11 | 0% | 4.1%（見第 4 節） |
| 馬來西亞 | daerah | 144 | 102 | 3% | 90% |

再往下一層的同樣指標，說明為什麼不繼續往下：

| 國 | 下一層 | 單位數 | 中位數 | 單點單位 | 中文單位 | 卡在哪一項 |
| :--- | :--- | ---: | ---: | ---: | ---: | :--- |
| 臺灣 | 村里 | 7,814 | 1 | 100% | 100% | 條件 2 |
| 南韓 | 읍면동 | 3,080 | 1 | 99% | 0% | 條件 2、4 |
| 泰國 | ตำบล | 7,423 | 1 | 100% | 0% | 條件 2、4 |
| 印尼 | desa | 63,513 | 1 | — | 0% | 條件 2、4 |
| 馬來西亞 | （無行政層） | — | — | — | — | 見下 |

兩個需要說明的例外：

**日本的密度是六國中最弱的，但沒有替代方案。** 中位數 1、62% 的市区町村只有
一個點，平均值 71.3 完全被離島型自治體拉高（小笠原村 4,812 點、石巻市 3,293、
長崎市 2,243——那是海岸與離島的每個多邊形各取一個中心點）。`admin_3` 只在
政令指定都市的區存在（171 個單位、覆蓋率 1.3%），不是全國性的層級，所以往下
走反而更不一致。市区町村本身通過條件 1、3、4，維持現況。

**馬來西亞下面沒有「更細的行政層」可選。** LocationIQ 的 address 物件在 MY
只提供到 daerah；其 `admin_3` / `admin_4` 欄位的值是門牌號、英里樁與建案名
（`14300`、`16英里`、`Alam Perdana`、`Amethyst 2`），不是行政區。再多查詢也
不會冒出 mukim，因為資料源沒有那一層，而且 LocationIQ 不提供 `admin_level`
或 `place_rank` 可供動態判定。

## 4. 印尼：換層級的取捨

印尼的 kecamatan 通過條件 1、2、3。條件 1 的落差是決定性的——kabupaten 平均
3,705 km²、每個名字涵蓋 53.6 萬人，比臺灣鄉鎮市區粗 37 倍，三格根本無法定位
座標：

| 座標 | kabupaten（舊） | kecamatan（現行） |
| :--- | :--- | :--- |
| 烏布 | 印尼・巴釐省・吉亞尼亞爾縣 | 印尼・巴釐省・Ubud |
| 婆羅浮屠 | 印尼・中爪哇省・馬格朗縣 | 印尼・中爪哇省・Borobudur |
| 水明漾 | 印尼・巴釐省・巴東縣 | 印尼・巴釐省・Kuta |

### 中文名來源查證（2026-09-14）

以 6,908 個 kecamatan 名稱逐批查 Wikidata（`?x rdfs:label ?name` + `P17=Q252`，
**不限 `P31` 類別**）：

| 查法 | kecamatan 名稱覆蓋 |
| :--- | ---: |
| 限定 `P31=Q3700011`（kecamatan 類別） | ~310 / 6,579（5%） |
| 不限類別、以名稱查 | **440 / 6,908（6.4%）**，點覆蓋 7.7% |
| 中文維基百科條目（限 kecamatan 類別） | 148 / 6,579（2%） |
| 國教院譯名表（NAER） | 結構性不適用（見下） |

**中文標籤往往掛在同名的聚落實體上，不在 kecamatan 實體上**，所以限定類別會
系統性漏掉：

| 地名 | 中文名所在實體 | 該實體的 `P31` |
| :--- | :--- | :--- |
| Ubud | 乌布（`Q210654`） | town |
| Seminyak | 水明漾（`Q1026424`） | kelurahan |
| Kuta | 庫塔（`Q994499`） | kecamatan |
| Ubud 的 kecamatan | 無（`Q3274172`） | kecamatan |

放寬類別的代價是雜訊：440 個命中裡有 64 個同名對到多個中文，其中包含語言與
族群（`Adonara → 阿多纳拉语`、`Banjar → 班查語`／`班查人`）與上一層行政區
（`Bandung → 萬隆縣`）。要採用必須經 P131 parent 驗證篩選，做法比照現有的
admin1／admin2 translator。

NAER 則對 handler 國家一律跳過（`naer_lookup.rs:240`，清單由 extract 的
`Country` enum 導出），因為 handler 名稱來自官方圖資、屬權威值，而 NAER 是
按名稱比對——`Alas` 會對到「阿拉斯海峽」而非同名的 kecamatan。

實際採用的是三來源彙整的 vendored 對照表
（`data/vendor/indonesia/kecamatan_zh.csv`，優先序 NAER → Wikidata → OSM），
收錄 286 個 kecamatan（329 列，同名的不同單位各自一列）：

| | kecamatan 有中文 | 點覆蓋 |
| :--- | ---: | ---: |
| 雅加達 | 39/44 | 249/417（59.7%） |
| 巴釐省 | 15/57 | 266/793（33.5%） |
| 西加里曼丹省 | 43/173 | 632/2,391（26.4%） |
| 全國 | 286/6,907（4.1%） | 5,433/107,961（5.0%） |

OSM 只在前兩者皆無、且中文字串逐字被 Wikidata 佐證時才收——峇里島有一批只
存在於 OSM 的機器產物（`Sidemen → 伴奏者` 是把英文樂手術語丟進翻譯器的結果），
拒收它們讓峇里島從 57 掉到 15，是刻意的取捨。來源與規則見
`data/vendor/indonesia/README.md`。

### 改層級的代價

同一份 GeoNames 快照、同一組旗標，只切換 `city_level`：

| | kabupaten | kecamatan |
| :--- | ---: | ---: |
| 印尼剪枝前點數 | 108,673 | 108,558 |
| 印尼剪枝後點數 | 30,992 | **83,333** |
| 印尼相異城市名 | 514 | **6,908** |
| 全球剪枝後總列數 | 305,088 | **358,447**（+17.5%） |
| 全球剪枝率 | 34.8% | 23.4% |
| 解壓後體積 | 62 MB | 67 MB |

標籤變細 14 倍，剪枝能證明的冗餘就大幅減少——印尼的刪除率從 71.5% 掉到
23.2%，全球輸出多出 53,359 列。這是辨識性的直接成本，已裁決接受。

實作與省份／時區細節見 [印尼行政區處理](indonesia-admin-processing.md)。

## 5. 新增國家時的檢查清單

1. 列出該國的行政層級與各層單位數
2. 從最細的那一層往上，逐層檢查四個條件；第一個全部通過的層級就是答案
3. 密度用 `data/handler/{cc}_geodata.csv`（或 LocationIQ CSV）在剪枝前算：
   每單位點數的中位數與單點單位比例
4. 中文覆蓋算「有中文名的單位比例」，不要算點覆蓋率——單位覆蓋率才反映
   使用者會看到幾種不同的中文名
5. 把結果補進本文件第 3 節的兩張表
