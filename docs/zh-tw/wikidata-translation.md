# Wikidata 譯名的已知失效形態

南韓、泰國與印尼 handler 以 Wikidata 解析行政區實體並取得繁體中文名稱。各國
用到的深度不同：TH 與 ID 直接採用 Wikidata 的中文 label；KR 的 admin1 走 handler
內建對照表，admin2 取自韓文維基條目中的漢字表記，Wikidata 主要負責認出實體與
驗證隸屬關係。

本文記錄實際遇過的失效形態、判別方式，以及現行防線的實際適用範圍。新增使用
Wikidata 的國家或更新既有國家的圖資時，請先讀過本文。

## 失敗是無聲的

問題大多不會中斷流程，而是安靜地流進輸出，且兩種結果的表現完全不同：

- **查不到實體，或所有候選都通不過隸屬驗證**：回退為來源原文，該地名在輸出中
  維持未翻譯。這種還算好認——它會出現在未翻譯清單裡。
- **選到錯誤的實體**：只要該實體通過 P131 隸屬驗證，譯名就取自該實體（可能經過
  簡繁轉換或改用中文維基條目標題）。這種最難察覺，因為輸出是合法的中文字串，只是
  指向錯的地方。首爾 `관악구` 曾輸出成「新林洞」，在未翻譯清單裡完全看不到。

唯一會當場停住的是 KR handler：admin1 解析不出 QID 時直接報錯，不讓下級行政區
退回以國家 QID 驗證。其他國家沒有這道防線。

因此驗證資料時**必須比對未翻譯名稱的完整清單，不能只看總數**。一個地名掉出、
另一個地名首次翻譯成功時，總數不會變。實際案例：印尼從舊版換到新版圖資時，未
翻譯的 `admin_2` 名稱數維持 51 個，逐筆比對才發現 `Kabupaten Ngawi` 掉了、另一
個地名補上。

未翻譯數量上升時要逐筆查明原因，不能直接視為來源新增了行政區——上游圖資新增
行政區與譯名失效兩者的表現一模一樣。

## 六種形態

以下為 2026 年 8 月的觀察。部分案例已回報並修正上游，因此照著「判別方式」重查
時未必仍能重現。

| 形態 | 案例 | 判別方式 |
| :--- | :--- | :--- |
| 搜尋選到錯誤實體（下級行政區、設施或機關） | 首爾 `관악구` 選到區內的 `신림동`；`송파구` 選到地鐵站 `잠실역`；`전남광주통합특별시` 選到同名的教育廳，導致 27 個下級行政區的 parent QID 全部指錯 | 候選的原文 label 與查詢名稱不相等 |
| 上游 label 停在舊制 | `여주시` 的中文 label 曾是 2013 年升格前的「驪州郡」；`검단구` 曾停在設區前的「黔丹面」 | 行政層級後綴與原文對不上（시→市、군→郡、구→區） |
| 宣稱為繁體的 label 字形有誤 | 兩種子型態：轉換選錯字（`함평군` 的 `zh-tw` label 曾把「咸」轉成「鹹」），以及根本沒轉換（印尼 Papua 的 `zh-hant` label 曾直接殘留簡體「巴布亚」） | 人工抽查，或以簡體字白名單掃描 |
| 缺少 `P131` 敘述 | `영종구` 設區後一段時間內完全沒有 | 隸屬驗證失敗且查無敘述 |
| `P131` 被標為 deprecated | 印尼 `Kabupaten Ngawi` 隸屬東爪哇省的敘述曾被標 deprecated | SPARQL 的 `wdt:` 前綴只走 best-rank statement，deprecated 等同不存在 |
| 我方過濾規則誤殺正確候選 | 關鍵字黑名單逐一檢查候選取回的每個 label，正確的 `관악구` 因 `zh-hant` 被機器人填成「冠嶽區廳」含「廳」字而被剔除 | 正確實體不在候選結果中 |

最後一種不是上游問題，是防護機制反噬。黑名單式的排除規則永遠列不完，而且會因為
某個無關語言的 label 誤傷正確候選。KR 已改用白名單式判定——原文 label 必須與查詢
名稱完全相符——機關、職位、選區、車站會自然落選。

> [!WARNING]
> **ID 路徑上仍保有同一個機制。** `indonesia_wikidata.rs` 的候選過濾會走訪
> `metadata.labels` 中的每個 label 比對排除關鍵字，與當初誤殺 `관악구` 的作法相同。
> 該表的內容取決於 `target_lang` 與 `fallback_langs`（ID 為 `zh-tw`、`zh-hant`、`zh`），
> 另外 `parse_entity_labels` 還會把 `zhwiki` / `kowiki` 的條目標題也放進同一張表，
> 等於連條目標題都掃。誤殺 `관악구` 的正是 `zh-hant` label，同樣落在這個範圍內。
> ID 目前未觀察到誤殺案例，但這是已知風險，調整印尼譯名時要留意。

## 現行防線與其範圍

這些防線多數是各國 handler 各自實作，共用層並未一體套用。新增國家時不能假設
已受保護。

| 防線 | 實作位置 | 適用範圍 |
| :--- | :--- | :--- |
| 候選過濾 | 各國自行提供 `candidate_filter` | 三國作法不同：KR 為韓文 label 全等比對，admin1 與 admin2 皆套用；ID 首輪即套用 instance-of 類別白名單，並額外以關鍵字黑名單比對取回的中文系 label 與條目標題；TH 的英文首輪**完全不過濾**，只有首輪失敗後改以泰文重試時才套用 instance-of 白名單 |
| parent QID 缺一即報錯 | `korea_admin2_parent_qids` | **僅 KR**。共用層的 `resolve_parent_qid` 仍會在查無 parent 時回退國家 QID，TH／ID 建表時則直接略過缺漏項目 |
| 行政層級後綴一致性 | `korea_admin2_level_matches` | **僅 KR admin2**。不符時回退韓文原名，會出現在輸出 CSV 的未翻譯清單中 |
| 簡體字偵測 | `WikidataTranslator::warn_if_simplified` | 共用層，但**只告警不改寫**——共用層自動簡轉繁會波及既有正確輸出 |
| 簡體字轉換 | `indonesia_normalize::fix_simplified_chars` | **僅 ID**。使用 `src/wikidata/simplified.rs` 的白名單，只轉換簡體獨有、無正體歧義的字 |

簡體字為何不用完整 OpenCC s2t：實測對真實印尼輸出套用完整 s2t 會改壞 24 個正確
譯名（`里→裏`、`占→佔` 等過度轉換），只修好 1 個。白名單只犧牲涵蓋率，不製造
新錯誤。

## 優先修正上游

某個譯名錯誤若源自 Wikidata 本身，**優先修正 Wikidata，而不是在本專案加對照表**。
修正上游對所有使用者都有效；對照表只對本專案有效，且需要長期維護。

南韓 handler 的實例：為了修正上游錯誤而規劃的七條人工對照表，在改用韓文維基的
漢字表記作為 admin2 名稱來源後降為零條——韓國行政區名本來就是漢字詞，漢字是原文
而非翻譯，與日本 handler 沿用圖資中的日文漢字同一原則。

（KR handler 另有兩份與上游錯誤無關的固定對照表：admin1 的內建譯名表，以及世宗
特別自治市的 admin2 對照表。世宗的下級行政區不經 Wikidata 查詢。）

## 快取

`geoname_data/{國碼}_wikidata_cache.json` 分為多層：`cache.search`、`cache.labels`、
`cache.instance_of`、`cache.p131` 存各階段的查詢結果，`translations` 存最終譯名決策
（key 格式 `<層級>/<國碼>/<上層行政區…>/<原名>`）。

`translations` 命中時要同時滿足兩個條件才會直接採用：本次算出的 parent QID 與
快取記錄的相同，且該筆結果為 `qid = null`（翻譯失敗）或 `parent_verified = true`。
兩者皆滿足時完全不查 `cache.p131`，因此**只清 `cache.p131` 對這類項目沒有任何
效果**。實務上絕大多數項目都落在這兩種情況裡。

- 修正上游單一實體後要重驗：該實體的 `cache.p131` 與 `translations` 兩處都要清。
  `cache.p131` 的 key 是 `<實體QID>_<上層QID>` 配對，翻譯失敗的項目在 `translations`
  裡沒有 QID，要從該項目的 `cache.search` entry 取得候選 QID 才找得到對應的 key。
- 修改候選篩選邏輯，或修改過上游 label：直接以空快取重跑。篩選邏輯還會吃
  `cache.search` 與 `cache.labels`，選擇性清除容易漏。
